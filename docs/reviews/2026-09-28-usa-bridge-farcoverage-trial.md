# USA Golden Gate partial far-coverage trial

The existing opt-in USA partial far-coverage path brings a red Golden Gate
bridge structure into the far-left view earlier than ordinary continuous 3×
drawing. A matched 40-frame live interval changes all 11 completed CRT images,
only in the far-left region. This is a visible, bounded benefit, **not** a
complete bridge, smooth handover, global pop-in fix or release-ready default.
The right-side dark dithered panel remains original game output in both modes.

## Why this trial was warranted

The earlier [object activation check](2026-09-28-usa-bridge-object-activation.md)
found three bridge objects appearing at different source frames. ROM model
radii showed that their centers being near 240,000 did not prove sphere
rejection. A new saved pre-activation state now narrows one case: a 10,472-input
replay of the same recorded drive passes original input/native comparison,
stable physical 2560×1440 display, literal FFB0 and owned shutdown. Its
**end-of-frame 10470** program/C31 RAM and immutable program ROM contain ready
future source `0x800a0040`, with a valid material, before its first logged host
submission at 10475. Independent offline reconstruction at the existing
240,000 limit emits zero ordinary target quads with a projection rejection;
the already gated partial-coverage mode emits three target quads at
native x −61..−42, y 144..185. This distinguishes a projection limitation in
that saved RAM state from missing residency. It is **not** exact source-time
camera/operand evidence at 10470 and does not classify the other bridge pieces.
The later [exact scene-hook capture](2026-09-28-usa-bridge-source-projection.md)
resolves that timing limit for frame 10473 and independently reproduces the
entire ordinary native scene before screening the same three target quads.

## Matched completed-image result

Frozen native `f762e01d63b` replayed the same 10,502 recorded inputs twice,
continuous USA 3×, CRT on and 4× internal scale on the physical 1440p primary.
The only renderer toggle was `--usa-host-far-coverage off/on`. Both raw run
reports **PASS** original input/native, display watch and owned shutdown;
their recorded frame clocks and inputs match exactly. Eleven completed
2544×1353 images span frames 10460..10500 every four frames. The off image at
10500 is byte-exact to the prior source-qualified capture.

All 11 images differ intentionally, 2,471–7,627 RGB frame-pixels each,
51,553 across the interval. Every changed pixel lies within x 103..243,
y 495..682; center and right remain exact. The candidate shows more of the
red bridge structure at 10460, before the control shows its larger pieces;
the two appearances move closer by 10500. A contact sheet is saved locally as
`usa-bridge-farcoverage-contact-v2.png`. The generic exact-image comparator's
**FAIL** is expected for an intentional visual change; the focused paired
qualifier separately **PASS**es motion, presentation bounds and shutdown.
Only 20 candidate-new near-black frame-pixels are detected by a color
heuristic; it is not a texture-defect count. The path submits 190,652 extra
auxiliary quads across the full prefix, but this count is not a quality score.

A separate offline color screen of these same 11 completed images uses the
fixed far-left `(70,450)..(290,710)` ROI, which contains all paired changes.
With the explicit predicate `R>110`, `100R>135G`, `100R>125B`, the candidate

at 10480..10500 as the control gains more red. The candidate's total red count

frame, the control has at most one red pixel absent in the candidate. This

include CRT color bleed or other red scenery. The source-hashed offline report
is `usa-bridge-red-transition-v1.json`; no additional game run was made.

These captures do not have an indexed original mirror or source-time packet
trace for the *new* pixels. Thus the visible result and offline three-quad

The existing partial-coverage switch remains diagnostic; no product default,
